# HarmonyOS Counter

[简体中文](./README_ZH.md) · [HarmonyOS integration](../../docs/harmony.md)

This example adds a TypeScript ViewModel to a native ArkUI page through a small, named facade. Copy its two source files into a **DevEco Studio Stage-model ArkTS application targeting API 12 or later**. The page uses `@ComponentV2` and `@Local`.

The repository validates the TypeScript facade and the generated package in Node. That does not compile the `.ets` page or validate it on a HarmonyOS device. Use the DevEco checks below before treating a particular SDK/device combination as supported.

## Files

| File                                                          | Responsibility                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| [CounterFacade.ts](./src/main/ets/viewmodel/CounterFacade.ts) | Business ViewModel, stable Spec, Scope ownership, commands, and a concrete `CounterSnapshot`. |
| [Index.ets](./src/main/ets/pages/Index.ets)                   | Component lifecycle and ArkUI rendering through `@Local count`.                               |

The example uses the local **OHPM package root** import, `@lwjlol/view_model`. The npm distribution exposes the same adapter as `@lwjlol/view_model/harmony`; change the import only when using that distribution in a TS/JS toolchain.

Harmony support is an **unreleased source addition**. The previously published npm `0.3.1` package does not include `/harmony`; build the OHPM package from this checkout. The npm import refers to a locally rebuilt package or a future release containing the adapter.

## 1. Build the local OHPM package

From this repository's root:

```sh
npm ci
npm run build:harmony
```

This produces `dist/ohpm`. Keep that directory available while a DevEco project uses it through a local dependency. These instructions do not assume the package has been published to the OHPM registry.

## 2. Create the DevEco application and install the dependency

Create a Stage-model **Empty Ability** application in DevEco Studio. Choose a compatible SDK and a minimum supported API of 12 or later for the V2 state-management example.

In the DevEco terminal, enter the application's `entry` module directory and install the generated package. Replace the path with the absolute path on your machine:

```sh
ohpm install /absolute/path/to/js_view_model/dist/ohpm
```

OHPM records a local dependency in `entry/oh-package.json5`. If the repository moves, update or reinstall that dependency. Run **Sync and Refresh Project** after installation.

## 3. Copy the source files

Copy the contents of this example's `src/main/ets` directory into the DevEco application's `entry/src/main/ets` directory:

- `viewmodel/CounterFacade.ts` remains a **`.ts`** file.
- `pages/Index.ets` replaces the generated counter page.

Keep the `EntryAbility` and project configuration generated by DevEco Studio. Its initial window should load `pages/Index`, as in a standard Empty Ability project. The page profile at `entry/src/main/resources/base/profile/main_pages.json` must include that path:

```json
{
  "src": ["pages/Index"]
}
```

If your project already has other pages, add or retain `pages/Index` alongside them instead of replacing the profile. No additional permissions or UIAbility code are required for this counter.

## 4. Build and verify in DevEco

Build and run the application on your selected simulator or device. Verify these behaviors:

1. The page initially displays `0`.
2. Each **Increment** tap updates the displayed count once.
3. **Recreate counter** force-recycles the generation and displays `0`; the next Increment tap displays `1`.
4. Hiding a retained page does not dispose its Scope. Returning to it retains the count while the process and component remain alive.
5. Removing/destroying the page invokes `aboutToDisappear`, which releases the Scope. A newly created page starts at `0`.

The last two checks require a navigation host if you want to exercise page retention explicitly. Backgrounding and foregrounding this single-page sample can check retention while the process stays alive, but it is not a substitute for the destruction check. In a new project, place a temporary breakpoint in `aboutToDisappear` when adding that navigation check.

## How state reaches the page

`aboutToAppear` creates a `CounterFacade` and obtains the initial snapshot. The facade owns one Scope, one Binding, and an independent Runtime. Its `getSnapshot()` calls `scope.watch(counterSpec)` to acquire the current ViewModel and returns a concrete snapshot containing a number.

Later, the Scope's stable `onUpdate` callback obtains another snapshot. The callback writes `snapshot.count` to ArkUI's `@Local count`, which is what the page renders. Re-resolving the Spec inside the callback also handles force recycle; the facade never holds a permanent reference to the old ViewModel.

The button action uses `scope.read(counterSpec)` because the action itself does not establish a rendering subscription. It still resolves the same generation already watched by this Scope. The Spec has no key, so a second facade gets an independent counter.

`aboutToDisappear` disposes the Scope without updating `@Local` fields. The Scope releases its Binding and the Runtime it created. There are no acquisitions or subscriptions inside `build()`.

## Lifecycle extension

This minimal example does not install an application foreground/background adapter. Page hiding alone does not dispose the Binding or pause the Runtime. To connect UIAbility lifecycle callbacks, use the explicit lifecycle bridge described in the [integration guide](../../docs/harmony.md#runtime-pause-and-application-lifecycle).

## Validation boundary

The repository's Node/TypeScript checks cover the facade, package exports, and adapter behavior. Only a successful DevEco build and the checks above establish that the `.ets` page, OHPM resolution, JS/ArkTS interoperability, and UI updates work with your selected HarmonyOS SDK. Keep the business file in TypeScript; renaming it to `.ets` changes the language constraints and is a separate migration.
